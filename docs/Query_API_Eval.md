# Query API / MCP Eval

**Run:** 2026-10-04, against the live database through the real `/mcp` endpoint (MCP SDK client →
local dev server → read-only analytics pool).
**Result:** 29 pass, 1 gap, 0 fail.
**Harness:** [`apps/web/scripts/mcp-eval.mts`](../apps/web/scripts/mcp-eval.mts), run with
`pnpm --filter web mcp:eval`. See the file header for the environment it needs.

## What this tests, and what it doesn't

Each question is answered by a scripted sequence of tool calls. The sequence was written from the
tool descriptions and server instructions alone, the way a model would read them. Where an
independent check exists, the answer is compared with a direct SQL query or another endpoint.

This tests the **tool contract**:

- The tools cover these questions.
- Arguments a model would naturally write are accepted.
- Results are correct.
- Errors carry what a model needs to recover (ambiguous names, metric aliases, unsupported game
  types).

It does **not** test whether a live model picks these calls. That needs a model in the loop, either
a client connected to `/mcp` or an Anthropic API tool-use harness. It is the next step once the
server is deployed.

## Findings

- **Ambiguity works as designed.** "Shadow" (two players) and "Brw" (a typo) come back as
  `ambiguous_player`, with candidates a user can choose between by home center and game count.
- **Fuzzy candidate order.** For "Brw", "Bru" (1 game) is listed above "Brew" (385 games),
  because candidates are ordered by spelling similarity first. The game counts make the right
  choice obvious, but weighting by games played would put the likely player first.
- **Lower-is-better metrics need `order` for "most" questions.** "Who gets penalized most?" needs
  `order: "desc"`, because `avg_penalties` defaults to best-first (fewest). The `order`
  description says so. Watch whether models get this right in live testing.
- **Gap: competition results.** "Who won Europe Championship 2026?" has no direct tool. The best
  effort is the last finals game. This is the `team_stats` / standings extension listed in the
  spec.
- **Data issue surfaced:** a Czech center's "Neutrální" team is stored as a competing team, so it
  shows as a third team that lost (#4, #30). This is filed separately as an ingest fix.
- **Latency:** tool calls averaged 7–32 ms, with a maximum of 115 ms (`player_stats` with
  head-to-head).
